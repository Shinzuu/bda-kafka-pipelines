Section 8.1From Batch ETL to Streaming Pipelines

ETL = Extract → Transform → Load. Standard for two decades. Easy for one pair of systems, catastrophic at organisational scale.

8.1.1 The N² Integration Problem

Each pair of systems exchanging data needs its own ETL job, so you count pairs:

N(N − 1) / 2  =  O(N²)

Bank example: 50 systems (core banking, CRM, risk, fraud, mobile wallet, settlement, audit, compliance) → 50 × 49 / 2 = 1,225 ETL jobs.

ProblemMeaning
BrittlenessSchema change in source A forces every job reading A to update simultaneously. A column rename becomes a multi-day incident.
No replayETL deletes from the source queue after consumption. Downstream offline when the job ran = data lost unless re-run from scratch.
High latencyNightly, hourly at best. Real-time fraud detection, live dashboards and event-driven personalisation are architecturally impossible.
Tight couplingAdding a consumer requires modifying or duplicating the source-side job.
Key Insight — the event bus Each system connects once: producers write to named topics, consumers subscribe. Adding a consumer requires zero changes to any producer. Total = 2N connections (one publish + one subscribe each) → O(N).
Figure 8.1 — each source is oblivious to the number of consumers.

8.1.2 The Tool Landscape

No single tool is optimal for all scenarios. Choice depends on data direction, latency requirement and operational complexity budget.

Section 8.2Batch Integration — Apache Sqoop and Apache Flume

8.2.1 Sqoop — bulk RDBMS↔HDFS

SQL-to-HadOOP. Command-line tool moving bulk data between any JDBC-compliant store (MySQL, Oracle, PostgreSQL, SQL Server) and HDFS, Hive or HBase.
Design insight: convert a table scan into a MapReduce job, each Map task reading a non-overlapping row range over its own JDBC connection.

StepImport pipeline
1Connect via JDBC, query table metadata: column names, types, primary-key range.
2Determine mapper count m (default 4). Split [kmin, kmax] into m equal-width sub-ranges.
3Submit the MapReduce job. Each Map task opens its own JDBC connection, runs the bounded SELECT, writes to HDFS as CSV, Avro, Parquet or SequenceFile.
4No Reduce phase. Each mapper writes an independent part file; HDFS assembles them.
sqoop import --connect jdbc:mysql://db-host:3306/finance \
  --table transactions --as-parquetfile --num-mappers 8 \
  --target-dir /data/raw/transactions --delete-target-dir

# incremental: only rows newer than the checkpoint
  --incremental append \
  --check-column txn_timestamp \
  --last-value '2024-06-11 23:59:59'

Incremental modes: append (new rows, value > checkpoint) and lastmodified (modification timestamp > checkpoint). The new checkpoint is stored in a saved job.
Export goes the other way — HDFS → RDBMS, e.g. a Spark summary table pushed back to MySQL for a BI tool (--update-mode allowinsert --update-key summary_date,region).

Why Sqoop is retired MapReduce dependency — incompatible with YARN-free deployments and cloud object stores. JDBC-per-mapper — hammers the source DB, often forcing a dedicated read replica. EOL 2021. Replaced by Kafka Connect + JDBC source connector: streaming incremental ingestion via CDC, no MapReduce, and Kafka replay semantics.

8.2.2 Flume — log ingestion

The unit is the agent: one JVM process, three components, a directed pipeline. The channel decouples source read speed from sink write speed, absorbing bursts.

ComponentJobTypes
SourceReceives eventsExec (tail -F), Syslog, Avro (from another agent), HTTP
ChannelBuffers between the twoMemory — fast, non-durable · File — disk, survives restart, costs throughput
SinkWrites to destinationHDFS, Kafka, HBase
agent.sources.nginx_src.type     = exec
agent.sources.nginx_src.command  = tail -F /var/log/nginx/access.log
agent.channels.file_channel.type = file
agent.sinks.hdfs_sink.hdfs.path         = hdfs://namenode:9000/logs/%Y/%m/%d
agent.sinks.hdfs_sink.hdfs.rollInterval = 300        # seconds
agent.sinks.hdfs_sink.hdfs.rollSize     = 134217728  # = 128 MB
Small files — the NameNode namespace tax A 10-second roll interval makes thousands of small files per day, each consuming a NameNode metadata entry and degrading NameNode heap.
Fix: roll every 300–600 s at 128 MB (one HDFS block). Or run a nightly compaction job (Spark, or Hive INSERT OVERWRITE … SELECT) merging into large Parquet files.
Fan-in — 20 servers, two tiers 20 edge agents (one per server): Exec/Syslog source → Memory Channel → Avro Sink.
2 collector agents (10 edge agents each): Avro Source → File Channel → HDFS Sink.
Buys durability (File Channel survives restart) and aggregation (20 writers → 2, cutting small-file pressure). Entirely config — no code required.
Section 8.3Apache Kafka — The Distributed Append-Only Log

Created by Jay Kreps, Neha Narkhede and Jun Rao at LinkedIn, 2010–2011, to solve the N² problem in LinkedIn's activity data pipeline. Open-sourced to Apache in 2012.

The central innovation Not an algorithm, not a hardware trick — a rethinking of what a message broker should be.
Traditional queues (ActiveMQ, RabbitMQ): messages are transient objects, deleted on acknowledgement.
Kafka: records in a durable, immutable, ordered log, retained regardless of consumption, readable by anyone at any offset.

8.3.1 The log abstraction

A log is an append-only, totally ordered sequence of records — the same abstraction as a database transaction log, a write-ahead log or a filesystem journal. Kafka's insight: what databases use for durability can be the backbone of a whole data infrastructure.

Record fieldPurpose
Key (optional)Determines partition assignment. Same key → same partition → key-level ordering preserved.
ValuePayload bytes — JSON, Avro, Protobuf, raw.
TimestampProducer- or broker-assigned event time.
OffsetMonotonically increasing integer assigned by the broker, unique within its partition.

Records are never modified or deleted within the retention period. The log is the single source of truth.

Figure 8.2 — delete-on-consume versus a retained log.

8.3.2 The five concepts

#ConceptWhat to say
1TopicNamed, durable, append-only log for a category of events. Like a database table but append-only.
2PartitionTopic split into P ≥ 1 ordered partitions, each an independent log on a single broker. Gives parallelism + key-based ordering.
3OffsetPosition in the partition log. Dense and ordered within a partition, NOT globally unique. The broker keeps no per-consumer state — consumers store offsets in __consumer_offsets.
4BrokerServer storing partitions. One leader replica handles all reads and writes; R−1 followers copy asynchronously and take over on failure. Default R = 3 → tolerates 2 broker failures.
5ZooKeeper / KRaftPre-3.0: ZooKeeper for metadata and leader election. Kafka 3.0 introduced KRaft, a self-managed quorum inside the brokers.

Figure 8.3: topic payment-txns, 3 partitions, RF = 2, 2 brokers. If Broker 1 fails, Broker 2 promotes its P0 and P1 replicas to leaders. Note RF = 2 here is the figure's value, not the default 3.

8.3.3 Producers, consumers, consumer groups

Producer picks the partition by hash(key) % P, or round-robin if no key. Batches in memory, sends to the leader in one request — batch.size and linger.ms trade latency for throughput.
Consumer polls and advances its own read offset. It never pushes back an acknowledgement to delete.

Consumer group A named set of consumers that collectively consume all partitions. Each partition is assigned to exactly one consumer in the group at any time.
  • Parallelism rises with consumers up to P; beyond that they idle.
  • Two applications both needing every message use two different groups — each keeps its own offsets.
  • A consumer joining or leaving triggers a rebalance. Kafka 2.4+ uses cooperative incremental rebalancing.
producer = KafkaProducer(bootstrap_servers="localhost:9092",
    batch_size=16384, linger_ms=5,   # 16 KB -- latency for throughput
    acks='all', retries=5)           # wait for ALL in-sync replicas
producer.send(TOPIC, key=str(txn["sender"]), value=txn)  # same sender -> same partition

consumer = KafkaConsumer(TOPIC, group_id="fraud-detection-v1",
    auto_offset_reset="earliest")    # start at offset 0 if new group

8.3.4 Throughput — 505,000 msg/s

Kreps et al. (2011): 505,000 messages/sec — roughly 11× ActiveMQ and 3.4× RabbitMQ on equivalent hardware. Four decisions explain it:

#DecisionDetail
1Sequential disk writesNever updates in place — appends to the active segment file. Sequential 500–600 MB/s vs random 50–100 MB/s (seek latency). The OS page cache prefetches, so speed nears raw disk bandwidth even without SSDs.
2Zero-copy transferTraditional: disk → kernel → user space → socket → NIC = 4 copies, 2 context switches. Kafka uses sendfile() to skip user space = 2 copies, 0 context switches. Halves CPU on read-heavy loads.
3Batch compressionProducer compresses a whole batch as one unit (Snappy, LZ4, Zstandard, GZIP). The broker stores it compressed without decompressing; consumers decompress. Ratio 5–10× on structured logs.
4Partition parallelismScales linearly with P. 1 → 32 partitions approaches 32×, bounded by broker and network capacity.
Key Insight — disk beats memory, for sequential access RAM wins for random access. For Kafka's sequential pattern the page cache makes disk faster than a heap structure at scale: sequential reads saturate the memory bus rather than L3 cache, and the kernel's LRU page cache is better tuned than a custom in-process cache.

8.3.5 Retention, replay, exactly-once

Retention: retention.ms default 7 days, or a size cap via retention.bytes. When both are reached the oldest segment files are deleted. A consumer slower than retention misses those messages — a deliberate choice prioritising throughput over guaranteed delivery to slow consumers.

Replay works because offsets are persistent and messages are not deleted on consumption. Three uses: backfilling a new service without re-ingesting from source · bug recovery by resetting to the last known-good offset · multi-consumer independence, a second group starting at offset 0 without affecting the first.

Exactly-once — Kafka 0.11 (2017)Mechanism
Idempotent producerMonotonically increasing sequence number per batch; the broker deduplicates duplicates from producer retries.
Transactional APISend to multiple partitions, then commit atomically or abort. With isolation.level=read_committed on the consumer, gives exactly-once across the full produce–consume–produce pipeline.
Schema Registry At 4,000 topics and 400 microservices (Netflix), a producer adding an Avro field without warning crashes every consumer. The Confluent Schema Registry registers each schema version under a subject, typically {topic}-value; producers embed the schema ID (an integer) and consumers look it up. It enforces a compatibility policy — BACKWARD, FORWARD, FULL — rejecting breaking changes. At Netflix and LinkedIn, non-negotiable in production.

Before you walk inThe traps that actually cost marks

1. O(N²) is the count of connections, not of systems N systems, up to N(N−1)/2 connections. The event bus is 2N connections — not N. Both publish and subscribe count.
2. Sqoop has no Reduce phase It is a map-only MapReduce job. Default mappers 4, not 1 and not 8. Eight was just the number in the sample command.
3. Memory Channel is fast, File Channel is durable Do not swap them. In the fan-in topology the edge agents use Memory Channel and the collector agents use File Channel — durability is bought once, at the collector tier.
4. Kafka offsets are per-partition Not per-topic, not global. Ordering is guaranteed within a partition only. Same key → same partition is what buys you per-key ordering.
5. The broker does not track consumer progress Consumers track their own offsets, stored in the __consumer_offsets topic. That statelessness is why replay is cheap.
6. Consuming does not delete Kafka deletes by retention policy (time or size), never on acknowledgement. That is the single biggest difference from ActiveMQ / RabbitMQ.
7. Zero-copy removes the user-space copy, it does not remove all copies 4 copies / 2 context switches → 2 copies / 0 context switches via sendfile(). Not "zero copies".
8. R = 3 tolerates 2 failures Replication factor R tolerates R−1 simultaneous broker failures. Default R = 3 → 2 failures.
